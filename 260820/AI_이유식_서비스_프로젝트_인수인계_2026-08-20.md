# AI 이유식 서비스 프로젝트 — 새 채팅 인수인계 문서

- 작성일: 2026-08-20
- 프로젝트명: AI 이유식 맞춤 플래너 / 이유식 레시피 웹사이트 + 앱
- 현재 역할: ChatGPT = Product Manager / UX / 서비스 아키텍처 / 데이터 모델 / 검증 담당
- 실제 개발: Claude Code가 담당
- 핵심 원칙: **그럴듯한 AI 답변보다 실제 개발 가능한 구조와 검증 가능한 데이터**

---

## 1. 프로젝트 한 줄 정의

아기의 이유식 단계와 부모가 선택한 재료/이유식 형태를 입력하면,

> **"오늘 무엇을 만들지" → "실제로 어떻게 만들지"**

를 연결해 주는 이유식 서비스.

단순 레시피 생성기가 아니라 **Ingredient Knowledge Base + 규칙 엔진 + 검증된 콘텐츠 + LLM** 구조를 목표로 한다.

---

## 2. 해결하려는 핵심 문제

현재 부모는 달력/메모에 다음 정도만 기록하는 경우가 많다.

- 8/20 완두콩
- 8/21 닭고기 + 단호박
- 8/22 소고기 + 브로콜리
- 퓨레 / 죽 / 토핑 / 자기주도식

하지만 실제 조리할 때 다시 검색해야 하는 정보가 많다.

- 어떻게 씻는가?
- 껍질을 제거해야 하는가?
- 씨/심/질긴 부분을 제거해야 하는가?
- 어떻게 자르는가?
- 삶는가 / 찌는가 / 굽는가?
- 얼마나 익혀야 하는가?
- 익었다는 것을 어떻게 판단하는가?
- 어떤 질감이 적절한가?
- 월령에 따라 어떻게 형태를 바꾸는가?
- 냉장/냉동/해동/재가열은 어떻게 하는가?
- 재료별 실패 포인트는 무엇인가?
- 질식/알레르기/위생 등의 주의사항은 무엇인가?

즉, 기존 서비스의 공백은 **계획과 실제 조리 사이의 정보 단절**이다.

---

11. 실전 TIP

# 4. 제품 설계 원칙

## 입력은 단순하게

가능하면:

> 재료 + 이유식 형태 + 월령

정도로 기본 레시피가 생성되도록 한다.

## 출력은 실제 조리가 가능해야 한다

"당근을 익혀주세요" 수준이 아니라 실제 손질과 상태 확인이 가능해야 한다.

단, 근거가 없는 조리 시간/온도를 임의로 만들지 않는다.

## 상태 기반 조리

서비스 차별점의 핵심 중 하나.

예:

> 포크로 눌렀을 때 쉽게 으깨지는 상태

같은 **상태 기반 익힘 기준**을 우선한다.

공식 근거가 없는 "찜기 10분", "전자레인지 3분" 같은 고정 숫자는 공식 DB 기준으로 넣지 않는다.

# 5. 안전성 원칙

영아가 섭취하는 식품이므로 일반 레시피 서비스보다 높은 안전 기준을 적용한다.

핵심 관리 영역:

- 월령별 적절성
- 질식 위험
- 알레르기
- 식품 위생
- 충분한 가열
- 보관/해동/재가열
- 생식/덜 익힌 식품
- 꿀 등 특별 주의 식품
- 소금/설탕 등 영아 식단 주의사항
- 견과류 및 기타 질식 위험 식품

안전 정보는 가능한 한 공식 소아과/공공기관/식품안전기관 원문을 우선한다.

확실하지 않으면 단정하지 않는다.

# 6. AI 사용 원칙

기본 구조:

> **구조화된 이유식 데이터 + 규칙 엔진 + 검증된 콘텐츠 + LLM**

- 사용자 입력 해석

- 개인화된 표현

핵심 안전/데이터:

- 재료 정보
- 월령/단계

- 손질법
- 조리법
- 익힘 상태

→ 가능한 한 구조화 데이터로 관리.

# 10. 경쟁 서비스 조사 결론

한국 시장을 중심으로 조사했을 때 경쟁 서비스는 이미 존재한다.

대표적으로 이유식 계획/기록/식단 관리/큐브 관리 등을 중심으로 한 서비스가 있다.

차별화 가능성이 높은 영역:

> **"재료 하나를 실제로 어떻게 손질하고 익히고 어떤 상태로 만들어야 하는가"**

특히:

- 전처리
- 껍질/씨/심 제거
- 상태 기반 익힘
- 질감
- 월령별 제공 형태
- 조리 실패 해결
- 실전 TIP

을 구조화한 **Ingredient Knowledge Base**가 차별점 후보.

또 하나의 차별점:

> **Cooking Mode**

조리 단계에서 현재 상태를 기준으로 다음 행동을 안내하는 방식.

# 11. 현재 데이터 조사 방식

현재는 초기 식재료를 대상으로 **Gemini와 Claude가 서로 독립적으로 조사**한다.

중요:

> Gemini 결과를 Claude에게 먼저 보여주고 검증시키지 않는다.

각 AI가 동일한 조사 범위를 독립적으로 조사한 뒤,

> **마지막에 Gemini 결과 vs Claude 결과를 비교**

한다.

이 방식의 목적은 한 AI의 잘못된 판단을 다른 AI가 그대로 따라가는 것을 방지하는 것.

# 13. 데이터 판정 체계

각 항목은 다음 중 하나로 판정한다.

### VERIFIED
신뢰할 수 있는 출처의 원문에서 해당 내용을 직접 확인.

### INFERRED
출처를 바탕으로 합리적인 추론은 가능하지만 원문에 직접 명시되지 않음.

### NEEDS_REVIEW
출처 간 차이, 해석 문제 또는 안전 관련 추가 확인 필요.

### UNSUPPORTED
신뢰할 만한 근거를 찾지 못했거나 출처가 주장을 뒷받침하지 않음.

근거가 없으면 억지로 VERIFIED로 만들지 않는다.

# 15. 반드시 지켜야 하는 검증 원칙

## 원문 확인

검색 결과 요약만 보고 판단하지 않는다.

실제 원문에서:

- 해당 내용이 존재하는지
- 영아에게 적용되는지
- 조건/예외가 있는지
- 권고인지 단순 설명인지

확인한다.

## 숫자 주의

다음은 특히 숫자를 임의 생성하지 않는다.

- 조리시간
- 조리온도
- 보관기간
- 재가열온도
- 월령
- 제공량
- 절단 크기

공식 근거가 없다면 UNSUPPORTED/NEEDS_REVIEW.

## "없음"과 "근거 없음" 구분

실제로 씨가 없는 식재료:

> 씨 제거 = 해당 없음

조사했지만 근거를 못 찾은 경우:

> 씨 제거 = UNSUPPORTED

## 일반 규칙과 식재료 고유 정보 분리

예를 들어 USDA의 일반 이유식 보관 원칙을 특정 식재료 고유 특성처럼 표현하지 않는다.

# 16. 현재까지 발견된 검증 이슈

최근 Gemini/Claude 결과를 검토하면서 다음과 같은 문제 유형을 발견했다.

## 두부

### 1) 간수 제거의 건강효과
"간수를 제거하면 영아의 장 자극/설사를 예방한다"는 식의 인과관계는 근거가 불명확하다.

→ DB에 바로 넣지 않는다.

### 2) 가열/생식
한국 권고와 해외 전문 이유식 자료 사이의 기준 차이를 추가 검증해야 한다.

### 3) 데치기 시간
"1~2분 데치기"가 공식 영아 이유식 기준인지 확인 필요.

---

## 사과

### 1) 생사과 제공 월령 내부 충돌
익힌 사과 / 강판에 간 생사과 / 통사과 기준이 결과 안에서 일관되지 않다.

→ 공식 질식 가이드와 전문기관 기준 재검증.

### 2) 베이킹소다 세척
구체적인 12~15분 베이킹소다 세척을 기본 이유식 세척법으로 DB에 넣을 필요가 있는지 의문.

→ 공식 식품안전기관 원문 확인 후 결정.

### 3) 껍질 제거 "필수"
실무적으로 제거를 권장할 수 있지만 "이유식 전 기간 필수"를 공식 안전 규칙처럼 저장하는 것은 재검토.

### 4) 냉동 보관
1~2개월과 3~6개월 등 기준이 충돌.

→ 공식 안전 기준과 품질 기준을 분리해서 검증.

### 5) 사과 알레르겐 가열
일부 알레르겐은 열에 영향을 받을 수 있지만 모든 사과 알레르기를 예방하는 것은 아니다.

→ "가열하면 알레르기 제거" 같은 표현 금지.

---

## 육류

### 1) 냉장 24시간
영아 이유식 전문가 자료와 일반 식품안전 기준이 섞여 있다.

→ "영아 이유식은 무조건 24시간"을 공식 규칙으로 저장하기 전에 원문 확인.

### 2) 씨 제거 필드 문제
닭고기에서 "씨 제거 = 뼈 제거"로 표현하는 것은 데이터 모델상 부적절하다.

→ `bone_removal` 또는 더 일반적인 `bone_fishbone_removal` 계열 필드를 별도로 검토.

### 3) 소고기 "고기가 최우선"
"철분이 중요한 시기"와 "고기가 최우선"은 같은 말이 아니다.

→ 과도한 표현을 완화.

### 4) 철분 흡수율 숫자
15~35%, <5% 등의 영양 수치는 MVP Ingredient DB 핵심 정보가 아니며 별도 검증 없이는 넣지 않는다.

---

## 연어

### 1) 다른 생선과 50% 교차반응
구체적인 숫자는 원 논문/전문기관 원문 확인 필요.

### 2) -20°C 7일 냉동
기생충 관리 기준과 이유식 조리 규칙이 섞일 위험이 있다.

→ 서비스에서 필요한 범위만 남기고 식품안전 원칙을 별도로 검증.

---

## 당근

당근 조사에서는 오히려 다음처럼 불확실성을 보존한 부분이 좋았다.

- 고정 조리시간 → UNSUPPORTED
- 일부 인터넷식 질산염 처리법 → 근거 부족 시 제외
- 상태 기반 익힘 → 활용 가치 높음

단, 당근 관련 특수 의학 이슈는 실제 근거가 있는지 확인 후 추가한다.

# 18. 데이터 모델 보완 필요

현재 조사 과정에서 확인된 개선점:

## 뼈/가시 제거 필드 추가

`seed_removal`을 뼈/가시 제거 용도로 재사용하지 않는다.

예:

- `seed_removal`
- `bone_removal`
- `fishbone_removal`

또는 더 일반화된 별도 전처리 구조를 설계할 수 있다.

## 근거를 데이터와 분리

가능하면 단순히 Ingredient에 `source` 하나만 두기보다:

> 데이터 항목 → Evidence → Source

구조로 어떤 주장에 어떤 근거가 붙는지 추적 가능해야 한다.

## 검증 상태 보존

각 핵심 데이터가:

- draft
- review
- verified
- deprecated

등의 상태를 가질 수 있어야 한다.

# 19. 현재 진행 방식

현재 단계:

> **Gemini/Claude 독립 식재료 조사 → 결과 비교 → 3차 원출처 검증**

순서.

### Step 1
초기 식재료 10개 조사.

### Step 2
Gemini 결과와 Claude 결과를 각각 모음.

### Step 3
두 결과를 항목별 1:1 비교.

### Step 4
다음 항목을 우선적으로 추림.

- 서로 다른 판단
- VERIFIED인데 근거가 약한 것
- 구체적인 숫자
- 영아 안전 관련 내용
- 출처가 실제 주장과 맞지 않는 것
- 일반 규칙과 식재료 고유 정보가 섞인 것
- AI가 과도하게 단정한 것

### Step 5
위 항목만 공식/전문기관 원문으로 3차 검증.

### Step 6
최종 검증된 데이터만 Ingredient DB에 등록.

# 22. 새 채팅에서의 작업 방식

사용자가 "계속 진행해"라고 하면 다음 의사결정 지점까지 스스로 진행한다.

불필요하게 매 단계마다 사용자에게 확인하지 않는다.

다만 다음과 같은 **실제 제품 의사결정이 필요한 순간**에는 사용자에게 질문한다.

예:

- DB 구조 선택
- MVP 범위 변경
- 안전 기준 간 충돌을 제품 정책으로 결정해야 하는 경우
- 사용자 UX 선택
- 개발 방식 선택

그 전까지는 ChatGPT가 조사/비교/검증/정리를 계속 진행한다.

# 23. 개발 전 최종 목표

최종적으로 Claude Code가 바로 구현할 수 있도록 다음 문서를 확정한다.

- 출처/evidence 구조
- 예외 처리
- 오류 처리
- 테스트 기준
- MVP 범위

핵심 구조:

> 사용자 입력  
> ↓  
> 구조화된 Ingredient / Stage / FoodForm 데이터  
> ↓  
> Safety Rule 검증  
> ↓  
> Recipe Assembly  
> ↓  
> 필요 시 LLM 자연어 구성  
> ↓  
> 최종 Safety Validation  
> ↓  
> 모바일 Cooking Mode 출력
