# Ingredient Role — MVP 제품 규칙 확정

- 작성일: 2026-08-26
- 근거 문서: [`docs/ingredient-role-analysis.md`](./ingredient-role-analysis.md)(50개 재료 판정),
  [`docs/ingredient-role-ux-analysis.md`](./ingredient-role-ux-analysis.md)(UX 적용 시 문제 분석)
- 목적: 위 두 문서에서 열어둔 제품 결정 사항 중, MVP에서 실제로 채택할 규칙을 확정한다.
- 범위: **제품 규칙 확정 문서.** 코드/DB/schema/seed는 전혀 수정하지 않았다. 실제 스키마 컬럼/
  마이그레이션/검증 로직 구현은 이 문서가 확정하는 규칙을 바탕으로 별도 작업에서 진행한다.

## 0. 이번 문서에서 먼저 정리하는 선행 사항

`ingredient-role-ux-analysis.md` §6에서 지적했듯, REVIEW로 묶였던 9종은 원인이 서로 다르다.

- **데이터 부족형 REVIEW (6종)**: broccoli, tofu, cucumber, corn, egg, chestnut — 근거가 없거나
  상충해서 보류.
- **이분법 불일치형 (3종)**: onion, mushroom, tomato — 근거는 있지만 base/topping 어느 쪽에도
  안 맞는, 별도 역할이 필요한 경우.

이 문서는 아래 결정을 통해 **onion/mushroom/tomato를 REVIEW가 아니라 `MIX_IN_ONLY`로 명시
재분류**한다(§1-2). 이 재분류 자체가 하나의 제품 규칙이며, 이후 REVIEW는 데이터 부족형 6종만을
가리킨다.

또한 `ingredient-role-analysis.md`에서 "topping만 보류"로 남겨둔 3종(napa_cabbage, cabbage,
spinach)은 base_eligible=TRUE가 이미 확정되어 있으므로, 이 문서에서는 "REVIEW"로 취급하지 않고
"BASE_AND_TOPPING 후보 중 topping 축만 미확정"으로 별도 취급한다(§4에서 처리 방식 확정).

## 결정 1. BASE_ONLY / TOPPING_ONLY / BASE_AND_TOPPING / MIX_IN_ONLY / REVIEW를 내부 role enum으로 사용할지

### 권고: **채택**

`ingredient-role-ux-analysis.md` §8-10에서 boolean 2축(B안)과 별도 매핑 테이블(D안)을 비교한
결과, 5값 enum(C안)이 가장 적절하다는 결론을 이미 내렸다. 이번 문서는 그 결론을 제품 규칙으로
확정한다.

| 평가 항목 | 내용 |
|---|---|
| 사용자 UX 영향 | enum 자체는 내부 데이터이며 사용자에게 직접 노출되지 않는다. 체감 영향은 결정 2-5가 이 enum을 검색 화면에 어떻게 매핑하느냐에 전적으로 달려 있다. |
| 기존 기능 회귀 가능성 | enum을 스키마에 "저장"하는 것과 검증 로직에서 "강제"하는 것은 분리할 수 있다. MVP에서는 저장은 하되, 결정 2-5에서 정한 만큼만 검증에 반영하는 점진적 적용을 전제로 하면 회귀 위험은 낮다. |
| 데이터 부족 문제 | REVIEW 값이 존재하므로 근거 부족을 "억지 분류" 대신 명시적으로 표현할 수 있다 — 오히려 데이터 부족을 안전하게 다루는 장치가 된다. |
| 향후 확장성 | 재료가 늘거나 역할이 세분화되어도 enum 값 추가로 대응 가능. 다만 role 축이 여러 개(계절성, 조리도구 등)로 늘어나는 시점에는 별도 매핑 테이블(D안)을 재검토할 필요가 있다(`ingredient-role-ux-analysis.md` §10 참고). |

## 결정 2. 주재료 검색에서 어떤 role을 노출할지

### 권고: **BASE_ONLY, BASE_AND_TOPPING, MIX_IN_ONLY, REVIEW(허용) 노출 / TOPPING_ONLY만 제외**

`TOPPING_ONLY`(김·참깨·들깨·치즈)만 주재료 검색에서 제외하고, 나머지는 모두 노출한다.
`MIX_IN_ONLY`(양파·버섯·토마토)는 별도 배지 없이 일반 재료와 동일하게 노출한다(§5에서 상술).
REVIEW 처리는 결정 4의 정책(주재료는 허용)을 그대로 따른다.

| 평가 항목 | 내용 |
|---|---|
| 사용자 UX 영향 | 김/참깨/들깨/치즈만 사라지고 나머지 46종은 지금과 동일하게 보인다. "김 퓨레"류의 무의미한 단독 조합이 원천 차단되어 오히려 결과물 품질이 개선된다. |
| 기존 기능 회귀 가능성 | TOPPING_ONLY 4종을 주재료로 선택하는 경로가 막힌다는 점에서는 기술적으로 기능 축소이지만, `docs/ingredient-role-analysis.md` §1에서 확신도 "높음"으로 판정된 조합(부피형 조리 근거 전무)이라 실질적 손실로 보기 어렵다. 단, 이 4종을 주재료로 이미 저장/공유한 레시피가 있다면 별도 마이그레이션 검토가 필요하다(이번 세션 범위 밖). |
| 데이터 부족 문제 | TOPPING_ONLY 판정 자체가 4종 모두 DB 근거 "높음"이라 오차단 위험이 낮다. |
| 향후 확장성 | 신규 재료 추가 시 role만 지정하면 노출 여부가 자동 결정된다. |

## 결정 3. 토핑 검색에서 어떤 role을 노출할지

### 권고: **TOPPING_ONLY, BASE_AND_TOPPING(단 topping 축이 확정된 것만) 노출 / BASE_ONLY, MIX_IN_ONLY, REVIEW, topping-미확정 3종 제외**

`BASE_ONLY`(쌀·오트밀·현미·보리)는 구조적으로 자기 자신 위에 얹힐 수 없으므로 제외한다.
`MIX_IN_ONLY`(양파·버섯·토마토)는 정의상 "독립적으로 얹는" 토핑 사용 패턴과 거리가 있으므로
토핑 화면에서 제외한다. `napa_cabbage/cabbage/spinach`는 base_eligible=TRUE가 확정됐지만
topping_eligible은 미확정(보류) 상태이므로, **MVP에서는 미확정 축을 "노출 안 함"으로 처리하는
보수적 기본값**을 적용한다(데이터는 여전히 "보류"로 유지하고, UI 노출만 잠정적으로 닫는다 —
"FALSE로 확정"하는 것과는 다르다).

| 평가 항목 | 내용 |
|---|---|
| 사용자 UX 영향 | 곡물 4종과 향미채소 3종이 토핑 목록에서 사라진다. "쌀 토핑", "양파 토핑" 같은 실제로 거의 쓰이지 않는 조합이 막혀 오히려 목록이 정돈된다. napa_cabbage 등 3종도 토핑에서 사라지지만, 이들의 topping 근거가 애초에 낮았으므로 체감 손실은 제한적이다. |
| 기존 기능 회귀 가능성 | BASE_ONLY 제외는 확신도 "높음"(DB+코드 근거)이라 회귀 리스크가 낮다. MIX_IN_ONLY·topping-미확정 3종 제외는 "아직 근거가 없어 잠정적으로 닫는다"는 성격이라, 근거가 보강되면 언제든 다시 열 수 있는 가역적 조치다. |
| 데이터 부족 문제 | topping-미확정 3종을 "닫힌 기본값"으로 두는 것은, 근거 없는 조합을 사용자에게 노출하는 리스크보다 선택지가 약간 줄어드는 불편이 더 안전하다는 판단에 기반한다. |
| 향후 확장성 | 세 재료의 topping 근거가 추후 보강되면 role 값만 `BASE_AND_TOPPING`으로 갱신하면 되고, UI 로직 변경은 필요 없다. |

## 결정 4. REVIEW 재료를 MVP에서 차단할지, 기존처럼 허용할지

### 권고: **비대칭 허용 — 주재료는 허용, 토핑은 차단**

REVIEW(데이터 부족형 6종: broccoli, tofu, cucumber, corn, egg, chestnut)를 완전 차단하지도,
완전 허용하지도 않는다. **주재료 검색에서는 지금처럼 계속 노출·선택 가능**하게 하고,
**토핑 검색에서는 노출하지 않는다.**

근거: 이 6종 모두 "주재료로 쓸 수 없다"는 근거는 없다(오히려 브로콜리 퓨레, 옥수수죽, 달걀찜,
밤죽처럼 흔히 쓰이는 조합들이다). 반면 "독립적으로 얹는 토핑"이라는 더 좁고 특수한 사용
패턴에 대해서는 형태 데이터 자체가 없어 근거가 훨씬 얇다. 즉 REVIEW라도 base 방향의 리스크와
topping 방향의 불확실성은 대칭이 아니다.

중요한 전제: **role 미확정이 안전 미검증을 의미하지 않는다.** broccoli/tofu/corn/egg/chestnut은
이미 `ingredient_safety_rules`(알레르기, choking 등)로 별도 안전 검증을 받고 있으며, 이 검증은
role 축과 완전히 독립적으로 계속 작동한다(예: corn의 CHOKING_HARD_RAW 규칙은 role과 무관하게
그대로 적용된다).

두 가지 대안과 비교:

| 옵션 | 사용자 UX 영향 | 회귀 가능성 | 데이터 부족 문제 | 확장성 |
|---|---|---|---|---|
| A. 완전 차단(양쪽 다 숨김) | broccoli/옥수수/달걀/밤처럼 실제로 자주 찾는 재료 6종이 검색 자체가 안 됨 — "재료가 왜 이렇게 적지" 하는 신뢰도 저하 위험 큼 | 매우 높음(명백한 기능 축소, 사용자가 체감) | role 불확실성과 안전 미검증을 혼동하는 처리 — 과잉 보수 | 데이터 보강 후 unblock 절차가 별도로 필요해 운영 부담 |
| B. 완전 허용(양쪽 다 노출, 현행 유지) | 지금과 체감 차이 없음 | 없음(현상 유지) | "두부 토핑", "브로콜리 토핑" 같은 근거 없는 조합이 계속 가능 — 다만 이는 이미 존재해온 위험이지 새로 생기는 위험은 아님 | role 데이터를 나중에 확정해도 자동 적용 안 됨(그때 가서 로직 추가 필요) |
| **C. 비대칭 허용(채택)** | 주재료는 지금과 동일, 토핑만 일부 조합(두부 토핑, 오이 토핑 등)이 줄어듦 — 애초에 어색한 조합이라 체감 손실 작음 | 주재료 쪽 회귀 없음, 토핑 쪽은 가역적 축소 | 불확실성의 방향에 비례해 리스크를 분산 처리 | topping 근거 보강 시 role 갱신만으로 자동 확장 |

## 결정 5. MIX_IN_ONLY를 MVP에서 별도 선택 영역으로 노출할지, 내부 role로만 유지할지

### 권고: **내부 role로만 유지 — 별도 UI 섹션을 신설하지 않고 주재료 검색에 통합 노출**

`MIX_IN_ONLY`(onion, mushroom, tomato — 3종)는 새로운 "향신·부재료" 선택 영역을 만들지 않고,
결정 2에 따라 기존 주재료 검색 목록에 배지 없이 그대로 포함시킨다.

| 평가 항목 | 내용 |
|---|---|
| 사용자 UX 영향 | 사용자 입장에서는 지금과 동일한 화면 — 새 UI를 학습할 필요가 없다. |
| 기존 기능 회귀 가능성 | 없음. |
| 데이터 부족 문제 | 이번 분석에서 MIX_IN_ONLY 후보는 3종뿐이다. 이 정도 규모로 새 선택 영역(신규 컴포넌트, 신규 상태, 신규 API 파라미터)을 만드는 것은 근거 재료 수 대비 과잉 투자다. |
| 향후 확장성 | 재료 데이터가 늘어나(예: 마늘·생강 등 향신료가 seed에 추가되어) MIX_IN_ONLY 부류가 유의미한 규모(예: 10종 이상)가 되면, 그때 별도 UI 섹션 신설을 재검토한다. 지금은 role 값만 구분해두고 화면은 통합하는 것이 CLAUDE.md §17 "MVP 단계에서는 불필요한 추상화도 피한다" 원칙에 부합한다. |

## 1. 최종 노출 매트릭스 (결정 2-4 종합)

| role | 재료(수) | 주재료 검색 노출 | 토핑 검색 노출 |
|---|---|:---:|:---:|
| BASE_ONLY | rice, oatmeal, brown_rice, barley (4) | O | X |
| TOPPING_ONLY | seaweed, sesame, perilla, cheese (4) | X | O |
| BASE_AND_TOPPING (양축 확정) | carrot, kabocha, potato, sweet_potato 등 31종 | O | O |
| BASE_AND_TOPPING (topping 미확정) | napa_cabbage, cabbage, spinach (3) | O | X (잠정) |
| MIX_IN_ONLY | onion, mushroom, tomato (3) | O (배지 없음) | X |
| REVIEW(데이터 부족형) | broccoli, tofu, cucumber, corn, egg, chestnut (6) | O | X |

TOPPING_ONLY 4종을 주재료 화면에서 "완전히 숨길지 vs 노출하되 선택만 비활성화할지"는
`ingredient-role-ux-analysis.md` §9에서 열어둔 질문이었다. MVP에서는 **완전히 숨기는 쪽**을
권고한다 — 비활성화 배지 방식은 `IngredientSearchOverlay`에 새 문구·상태를 추가해야 하는 반면,
완전 숨김은 노출 대상 목록만 필터링하면 되어 구현이 더 단순하다(§17 MVP 원칙). BASE_ONLY 4종을
토핑 화면에서 제외하는 방식도 동일하게 완전 숨김을 권고한다.

## 2. 최종 권고안 (하나로 통합)

1. **role enum 도입**: `BASE_ONLY | TOPPING_ONLY | BASE_AND_TOPPING | MIX_IN_ONLY | REVIEW` 5값을
   내부 데이터로 사용한다.
2. **onion/mushroom/tomato는 REVIEW가 아니라 MIX_IN_ONLY로 명시 분류**한다 — 데이터 부족이
   아니라 이분법 불일치가 원인이므로.
3. **주재료 검색**: TOPPING_ONLY(4종)만 제외하고 전부 노출(완전 숨김 방식).
4. **토핑 검색**: TOPPING_ONLY + BASE_AND_TOPPING(topping 축 확정분)만 노출. BASE_ONLY,
   MIX_IN_ONLY, REVIEW, topping-미확정 3종은 제외(완전 숨김 방식, 단 근거 보강 시 가역적).
5. **REVIEW(데이터 부족형 6종)는 주재료만 허용, 토핑은 차단** — role 미확정과 안전 미검증을
   혼동하지 않는다는 전제하에.
6. **MIX_IN_ONLY는 별도 UI 섹션을 만들지 않고 주재료 화면에 통합** — 3종이라는 현재 규모에서는
   신규 UI 투자가 과잉이다.

이 권고안은 `ingredient-role-ux-analysis.md`가 지적한 6가지 문제(§1-6)를 다음과 같이 해소한다:
TOPPING_ONLY/BASE_ONLY의 구조적 모순 조합이 제거되고(§4-5 문제), MIX_IN_ONLY 재료가 "사용
불가"로 오독될 위험 없이 계속 선택 가능하며(§6-7 문제), REVIEW 재료는 근거 부족 방향에 비례해
비대칭적으로 처리되어 완전 차단으로 인한 서비스 신뢰도 손상을 피한다(§3 문제). 다만 §2에서
지적한 "중복 선택(같은 재료를 주재료+토핑에 동시 선택)" 문제와 확신도 노출 여부는 이번
권고안의 범위 밖으로 남겨두며, 별도 제품 논의가 필요하다.

이 문서는 제품 규칙 확정 문서이며, 위 규칙을 실제 스키마 컬럼·마이그레이션·검증 로직에
반영하는 구현은 별도 작업으로 진행한다.
