# Phase 11 — UI/UX 1차 개편 구현 지시서

## 1. 작업 목적

현재 MVP의 백엔드/API/DB/안전 검증 구조는 유지하고, 지금까지 확정한 제품 UX를 기준으로 **모바일 우선 UI/UX를 1차 개편한다.**

이번 작업의 목적은 새로운 기능을 무작정 추가하는 것이 아니다.

핵심 사용자 흐름을 다음과 같이 단순하고 빠르게 만드는 것이다.

> 아기 홈 → 이유식 만들기 → 단계 선택 → 재료 선택 → 이유식 형태 선택 → 레시피 생성 → 레시피 확인 → Cooking Mode

실제 부모가 스마트폰을 들고 빠르게 이유식을 만들 수 있는 UX를 우선한다.

---

# 2. 절대 변경하지 말아야 할 것

이번 작업에서 아래 기존 시스템은 **기능적으로 변경하거나 삭제하지 않는다.**

### Backend / Data

- Supabase 연결
- 기존 migration
- 기존 seed 데이터
- Ingredient 데이터 구조
- cooking_profiles
- texture_profiles
- evidence
- safety rules
- validation rules
- recipe generation logic
- unsupported ingredient 차단 로직
- allergen safety logic

### API

기존 API 계약을 유지한다.

- GET /api/v1/stages
- GET /api/v1/food-forms
- GET /api/v1/ingredients
- GET /api/v1/ingredients/:id
- POST /api/v1/recipes/validate
- POST /api/v1/recipes/generate

기존 응답 필드를 삭제하거나 이름을 변경하지 않는다.

### 테스트

기존 테스트가 깨지면 UI 작업을 중단하고 원인을 확인한다.

기존:

- unit tests
- safety tests
- integration tests
- lint
- typecheck
- build

모두 유지한다.

# 3. 이번 Phase에서 하지 않을 것

다음 기능은 이번 UI 개편 범위에 넣지 않는다.

- 로그인
- 회원가입
- 여러 아기 프로필

- 사진의 Supabase Storage 업로드
- 추천 재료 알고리즘
- 전체 재료 목록을 기본 화면에 노출
- 재료 상세 페이지를 별도로 만드는 것
- 이유식 기록 기능
- 장보기 기능
- 알레르기 기록 기능
- 푸시 알림
- 조리시간 데이터를 임의로 추가
- 근거 없는 재료 데이터 추가

# 4. 아기 프로필 / 홈 화면

## 4-1. 신규 사용자

아기 프로필이 없는 사용자는 기존 온보딩을 이용한다.

입력:

- 아기 이름
- 생년월일
- 아기 사진 (선택)

생년월일을 기준으로 생후일수를 자동 계산한다.

이유식 단계 역시 현재 로직을 이용해 추천한다.

사진은 현재 설계대로 **localStorage에만 저장**한다.

Supabase DB/Storage에 업로드하지 않는다.

사진 선택 UI에는 단순히:

> 사진 추가 (선택)

정도로 표시한다.

"DB에 저장되지 않습니다" 같은 기술적인 설명은 기본 UI에 노출하지 않는다.

# 5. 아기 홈 화면

프로필이 저장된 사용자는 재방문 시 온보딩을 건너뛰고 바로 아기 홈으로 들어온다.

홈은 크게 **상단 / 하단** 두 영역으로 단순화한다.

## 상단

- 아기 사진
- 아기 이름
- 생후일수
- 현재 이유식 단계
- 추천 단계라면 별표 표시

예:

> [아기 사진]
>
> 아인
>
> 생후 187일 · 초기 ⭐

사진이 없는 경우 적절한 기본 placeholder를 사용한다.

## 하단

가장 중요한 CTA 하나를 중심으로 구성한다.

> 🍚 오늘 이유식 만들기

버튼은 모바일에서 충분히 크고 쉽게 누를 수 있도록 한다.

홈 화면에 최근 재료, 전체 재료 목록, 복잡한 정보 등을 넣지 않는다.

### 우측 상단 메뉴

`⋯` 메뉴를 사용한다.

MVP에서는 최소 기능만 제공한다.

- 아기 정보 수정
- 사진 변경

불필요한 초기화 기능이나 아직 존재하지 않는 기록 기능은 추가하지 않는다.

---

# 6. 이유식 만들기 화면

홈에서 `오늘 이유식 만들기`를 누르면 `/plan`으로 이동한다.

이 화면은 **상단 / 중단 / 하단** 구조로 단순하게 만든다.

---

## 6-1. 상단 — 이유식 단계

화면 상단에 단계 선택을 배치한다.

단계는 **2×2 카드가 아니라 한 줄로 나열한다.**

예:

> 이유식 단계
>
> `[ 초기 ⭐ ] [ 중기 ] [ 후기 ] [ 완료 ]`

추천 단계는 기본 선택되어 있어야 한다.

추천 단계는 **박스/테두리 + ⭐ 정도로만 표시**한다.

긴 설명문:

> "아기의 생후일수에 따라 초기 이유식 단계가 추천됩니다..."

같은 문장은 기본 UI에서 제거한다.

사용자가 원하면 다른 단계로 변경할 수 있다.

---

# 7. 재료 선택

재료 선택 영역은 이유식 만들기 화면의 핵심이다.

## 7-1. 추천 재료

이번 MVP에서는 **추천 재료 영역을 만들지 않는다.**

추천 기준이 아직 확정되지 않았기 때문이다.

나중에 별도 기능으로 추가할 수 있도록 구조만 깨지지 않게 한다.

---

## 7-2. 전체 재료 목록

기본 화면에서 수십~수백 개의 재료를 전부 펼쳐놓지 않는다.

기존의 5행 × 2열 전체 재료 카드 UI가 있다면 제거하거나 기본 노출하지 않는다.

---

## 7-3. 검색

재료 검색창을 가장 위에 배치한다.

예:

> 재료
>
> `[ 🔍 재료를 검색해보세요 ]`

검색창을 누르면 **별도의 검색 화면**으로 이동한다.

검색 화면:

> ← 재료 검색
>
> `[ 🔍 당근 ]`
>
> 검색 결과
>
> 당근
> 채소 · 준비됨

검색 결과는 **세로 리스트**로 구성한다.

2열 카드 형태를 사용하지 않는다.

향후 재료가 수십~수백 개가 되어도 검색할 수 있도록 검색 로직은 데이터 규모 증가를 고려한다.

---

# 8. 검색 결과에서 재료 선택

검색 결과에서 재료를 누르면 **바로 현재 선택 재료에 추가**한다.

별도의 재료 상세 확인 → 선택 버튼 같은 중간 단계를 만들지 않는다.

예:

검색:

> 당근

사용자가 당근을 누르면:

> `[ 당근 × ]`

형태로 현재 선택 영역에 추가된다.

검색 화면에서 선택 후 기존 이유식 만들기 화면으로 돌아갈 수 있어야 한다.

---

# 9. 현재 선택 재료와 최근 선택 재료는 반드시 구분

이 둘을 혼동하지 않는다.

## 현재 선택 재료

현재 만들 레시피에 사용할 재료.

예:

> 선택한 재료
>
> `[ 당근 × ] [ 소고기 × ]`

`×`를 누르면 현재 선택에서 제거한다.

여러 재료를 동시에 선택할 수 있어야 한다.

---

## 최근 선택 재료

사용자가 과거에 실제로 **레시피 생성까지 완료한 재료**를 빠르게 다시 선택하기 위한 영역이다.

단순히 검색해서 눌렀다고 최근 선택으로 저장하지 않는다.

예:

검색 → 당근 선택 → 취소

이 경우 최근 선택에 당근을 추가하지 않는다.

레시피 생성 완료:

> 당근 + 소고기

이후 해당 재료들이 최근 선택 데이터에 반영된다.

최근 선택은 MVP에서는 현재와 동일하게 localStorage 기반으로 처리해도 된다.

---

# 10. 이유식 형태

재료 선택 영역 아래에 이유식 형태를 배치한다.

한 줄 버튼 방식으로 구성한다.

예:

> 이유식 형태
>
> `[ 죽 ] [ 퓨레 ] [ 토핑 ] [ BLW ]`

선택된 형태를 명확하게 강조한다.

별도의 형태 추천 알고리즘은 이번 작업에서 추가하지 않는다.

이유식 형태 바로 아래에 CTA를 배치한다.

> `[ 🍚 레시피 만들기 ]`

이번 단계에서는 화면 하단 고정 버튼을 만들지 않는다.

선택 항목 바로 아래에서 자연스럽게 누를 수 있게 한다.

---

# 12. 레시피 생성 로딩

레시피 생성 버튼을 누른 뒤 짧은 로딩 UI를 표시한다.

과도한 애니메이션은 사용하지 않는다.

예:

> 🥕 재료를 확인하고 있어요
>
> 아기에게 맞는 레시피를 준비하고 있어요...

짧고 자연스러운 로딩 상태를 사용한다.

---

# 13. 레시피 결과 화면

레시피 화면은 **정보를 전부 보여주는 백과사전 형태가 아니다.**

역할은:

> "오늘 뭘 만들고, 어떻게 하는지 빠르게 이해하는 화면"

이다.

다음 정보를 간결하게 구성한다.

1. 오늘의 이유식 이름
2. 짧은 설명
3. 재료
4. 손질
5. 조리 방법
6. 익힘 확인
7. 질감/제공 형태
8. 보관 정보
9. 주의할 점 / 안전 경고
10. Cooking Mode 진입 CTA

특히 **주의할 점 / 안전 경고는 반드시 눈에 띄게 포함한다.**

단, 기존 DB/API에 존재하는 검증된 정보를 사용하며 새로운 안전 정보를 임의 생성하지 않는다.

예:

> ⚠️ 주의할 점
>
> - 닭고기는 내부 온도 73.9°C 이상까지 충분히 익혀주세요.
> - 뼈가 남아 있지 않은지 확인해주세요.

# 14. Cooking Mode

Cooking Mode는 레시피를 실제로 조리하면서 보는 화면이다.

기존 STEP 기반 구조를 유지하면서 모바일에서 보기 쉽게 개선한다.

기본 구조:

> STEP 2 / 5
>
> 당근을 익혀주세요.
>
> 포크로 눌렀을 때 쉽게 으깨질 정도까지 익혀주세요.
>
> [ 상태/익힘 확인 ]
>
> ⏱ 03:24
>
> [ 다음 STEP ]

# 15. 타이머 요구사항

**타이머는 반드시 구현한다.**

단, 카운트다운이 아니라 **카운트업(경과시간)** 방식이다.

예:

> ⏱ 03:24

사용자가 조리를 시작하면 시간이 올라간다.

## 조리시간 데이터가 있는 경우

검증된 조리시간 데이터가 존재한다면:

> 권장 조리시간: 10분
>
> ⏱ 03:24

처럼 표시할 수 있다.

하지만 해당 데이터가 없는 경우:

> ⏱ 03:24

처럼 단순 경과시간만 제공한다.

**근거 없는 조리시간을 생성하거나 추가하지 않는다.**

즉:

- 타이머 기능 = 항상 제공
- 권장 조리시간 = 데이터가 있을 때만 표시
- 데이터가 없으면 빈칸이나 임의 숫자를 표시하지 않음
- 카운트다운 ❌
- 카운트업 ✅

사용자가 별도의 스마트폰 타이머 앱을 사용할 필요가 없도록 하는 것이 목적이다.

---

# 16. 디자인 방향

이번 작업은 기능보다 **실제 모바일 사용성**을 우선한다.

원칙:

- 모바일 우선
- 한 화면에서 핵심 정보가 빠르게 들어와야 함
- 과도한 카드 남발 금지
- 과도한 텍스트 금지
- 버튼은 충분히 크게
- 선택 상태는 명확하게
- 추천 단계는 ⭐ + 박스로 직관적으로 표시
- 귀엽지만 유아용 장난감 같은 과도한 디자인은 피함
- 부모가 요리하면서 한 손으로 보기 쉬워야 함
- 화면 이동을 최소화하되 검색처럼 별도 화면이 실제로 유리한 경우는 분리

현재 프로젝트의 기존 디자인 시스템/컴포넌트가 있다면 최대한 재사용한다.

# 17. 반응형

반드시 모바일을 최우선으로 확인한다.

특히 다음을 확인한다.

- 320px
- 375px
- 390px
- 430px

가로 스크롤이 생기지 않도록 한다.

단계 버튼은 한 줄로 유지하되, 화면 폭에 맞게 글자 크기/간격을 조정한다.

단계 버튼 때문에 가로 스크롤을 만들지 않는다.

# 19. 테스트 기준

다음 플로우를 실제 브라우저에서 검증한다.

### 신규 사용자

온보딩
→ 이름 입력
→ 생년월일 입력
→ 사진 선택 또는 생략
→ 단계 추천
→ 아기 홈

### 재방문

새로고침
→ 온보딩이 다시 나오지 않음
→ 아기 홈 진입

### 이유식 생성

아기 홈
→ 오늘 이유식 만들기
→ 추천 단계가 기본 선택
→ 다른 단계로 변경 가능
→ 재료 검색
→ 검색 결과 세로 리스트
→ 재료 선택
→ 현재 선택 재료 표시
→ 다른 재료 추가
→ 재료 제거
→ 이유식 형태 선택
→ 레시피 생성

### 최근 재료

검색만 하고 취소
→ 최근 선택에 추가되지 않음

레시피 생성 완료
→ 최근 선택에 반영

재방문
→ 최근 선택 유지

### Cooking Mode

레시피
→ Cooking Mode
→ STEP 이동
→ 타이머 시작
→ 카운트업
→ STEP 이동
→ 타이머 상태 정상 처리

# 21. 중요한 작업 방식

이번 작업에서 **디자인을 한 번에 완벽하게 확정하려고 하지 않는다.**

먼저 위 요구사항을 기준으로 1차 UI를 구현한다.

구현 후:

1. 실제 브라우저에서 전체 플로우 확인
2. 모바일 화면 확인
3. 스크린샷으로 주요 화면 확인
4. 발견된 UX 문제를 목록화
5. 기존 기능 regression 여부 확인

까지만 진행한다.

**추가 기능이나 임의의 UX를 새로 만들지 않는다.**

이번 Phase의 결과물은 "완성된 최종 디자인"이 아니라 **사용자가 실제로 테스트할 수 있는 UI/UX 1차 버전**이다.
