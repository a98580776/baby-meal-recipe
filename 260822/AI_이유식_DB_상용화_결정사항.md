# AI 이유식 서비스 — DB 설계 및 조사 결정사항

## 1. 현재 프로젝트 상태

- UI/UX Phase 11 수정사항은 실제 반영 및 배포 확인 완료.
- 당분간 UI는 동결하고 DB 작업으로 진행.
- 다음 핵심 작업은 **이유식 재료 DB의 상용화 기준 데이터 구축**.
- 기존 10개 재료를 먼저 재검증한 뒤 재료 수를 확장한다.
- 첫 번째 기준 재료는 **당근**으로 한다.

---

## 2. 제품의 DB 기본 원칙

이 서비스는 단순 레시피 생성기가 아니라:

> 재료 + 이유식 단계 + 형태 → 실제 조리에 필요한 검증된 정보

를 제공하는 서비스다.

LLM이 모든 정보를 임의 생성하지 않고:

> 구조화된 데이터 + 규칙 엔진 + 검증된 콘텐츠 + LLM

구조를 기본으로 한다.

핵심 데이터는 가능한 한 구조화해서 관리한다.

---

## 3. 데이터 완성 기준

### 기본 원칙

재료의 모든 정보가 완벽하게 존재해야만 서비스에 노출시키는 방식은 사용하지 않는다.

예:

- 손질 ✅
- 조리방법 ✅
- 질감 ✅
- 안전정보 ✅
- 조리시간 ❌
- 보관정보 ❌

이라도 재료 자체는 서비스에서 사용할 수 있다.

대신 근거가 없는 개별 정보만 `미등록` 처리한다.

### 절대 금지

- 근거 없는 조리시간 추정
- 근거 없는 보관기간 추정
- 근거 없는 안전정보 생성
- AI가 빈 데이터를 그럴듯하게 채우는 것
- 인터넷 민간요법/육아 속설을 사실처럼 등록

---

## 4. 데이터별 결정사항

### 4.1 질감(Texture)

**결정: C**

출처에서 제공하는 연령/형태 정보를 서비스의 4단계로 합리적으로 매핑한다.

4단계:
- 초기
- 중기
- 후기
- 완료기

출처가 반드시 "초기/중기/후기/완료기"라는 표현을 그대로 사용해야 하는 것은 아니다.

예를 들어 출처의 연령 범위/제공 형태 정보를 우리 서비스 단계에 합리적으로 매핑할 수 있으면 등록한다.

단, 매핑이 불확실하면 `NEEDS_REVIEW`, 근거 자체가 없으면 `UNSUPPORTED/미등록`.

입자 크기 등 숫자값은 근거가 없으면 임의 생성하지 않는다.

---

### 4.2 조리방법(Cooking Method)

**결정: C**

가능한 조리방법은 모두 저장한다.

예:
- 찌기 ⭐
- 삶기
- 굽기

그리고 서비스에서 기본으로 제시할 **추천 조리방법 1개**를 별도로 지정한다.

추천 방법은 AI가 임의로 선택하지 않고 근거와 이유를 가지고 DB에서 지정한다.

---

### 4.3 조리시간(Time Guidance)

**결정: A**

공식/공신력 있는 근거에서 확인된 시간만 DB에 저장한다.

근거가 없으면:
- 시간 데이터를 만들지 않는다.
- AI 추정값을 사용하지 않는다.
- 사용자에게 수동 count-up 타이머를 제공한다.

또한 조리시간은 단순히 재료에 붙는 값이 아니라:

> 조리방법 + 조리 형태(cut/form 등) + 시간

관계로 관리할 수 있어야 한다.

예:
- 찌기 → 10분
- 삶기 → 8분

출처에 따라 시간 측정 기준(예: 끓기 시작 후인지 등)이 명확하다면 해당 조건도 함께 관리한다.

---

### 4.4 익힘 확인(Completion Check)

조리시간이 있더라도 최종적으로는 **익힘 상태를 확인할 수 있는 방법**을 제공한다.

시간만으로 완료를 판단하지 않고 필요한 경우:
- 포크로 눌렀을 때
- 쉽게 으깨지는지
- 내부 상태
등의 상태 확인 기준을 사용한다.

단, 근거 없는 안전/익힘 기준은 임의 생성하지 않는다.

---

### 4.5 보관(Storage)

**결정: A**

공식/공신력 있는 근거가 확인된 경우에만 등록한다.

상용화 시 확장 가능한 데이터:
- 보관 방법
- 보관 조건
- 보관 기간
- 식품 상태(food_state: 생재료/익힌 재료/조리된 이유식 등)
- 해동 방법
- 재가열 필요 여부
- 재가열 관련 주의
- 조리 후/개봉 후 기준
- Evidence

근거 없는 기간을 임의로 넣지 않는다.

---

### 4.6 안전(Safety)

**결정: A**

공식/공신력 있는 근거가 확인된 안전정보만 등록한다.

예:
- 질식 위험
- 알레르기 관련 주의
- 충분히 익혀야 하는 식재료
- 씨/껍질/뼈/가시 관련 안전사항
- 생식/덜 익힌 식품 위험
- 제공 형태에 따른 위험
- 월령 관련 제한

Safety는 단순 Ingredient 텍스트 하나로 몰아넣지 않고 별도의 Safety Rule 개념으로 관리한다.

Safety Rule에는 가능하면:
- rule_type
- severity
- condition
- action
- reason/description
- evidence
- status
등을 둘 수 있도록 한다.

---

### 4.7 손질/전처리(Preparation)

**결정: C**

일반적인 조리 지식으로 명백한 손질 과정은 허용한다.

예:
- 씻기
- 껍질 벗기기
- 꼭지 제거
- 일반적인 자르기

그러나 영아 안전과 직접 연결되는 손질은 공식/공신력 근거를 우선한다.

예:
- 질식 위험 때문에 특정 형태를 피해야 하는 경우
- 뼈/가시 제거
- 씨 제거 등 안전 관련 조건

일반 조리 지식과 안전 근거가 필요한 정보를 구분할 수 있도록 한다.

---

### 4.8 TIP

**결정: B**

실제 조리에 도움이 되는 일반적인 조리 지식/경험적 팁은 허용한다.

예:
- 껍질을 익힌 후 제거하면 편한 경우
- 물기가 너무 많거나 적을 때 조절하는 방법
- 손질 시간을 줄이는 방법
- 으깨기 쉽게 만드는 방법

단:
- 안전과 직접 관련된 TIP은 공식/공신력 근거 필요
- 민간요법/근거 없는 육아 상식 제외
- AI가 그럴듯하게 만들어낸 TIP을 검증 없이 등록하지 않음

---

### 4.9 알레르기(Allergen)

**결정: C**

알레르기 정보는 가장 엄격하게 관리한다.

- 공식/공신력 출처에서 확인된 알레르겐 분류만 등록
- 확인되지 않으면 추정하지 않음
- 향후 아기 프로필의 알레르기 차단 로직과 연결될 수 있으므로 핵심 안전 데이터로 취급

---

## 5. Evidence(근거) 관리

**결정: C**

상용화 기준으로 데이터가 어느 근거에서 왔는지 추적 가능해야 한다.

다만 모든 컬럼에 단순히 `evidence_id`를 무작정 붙이는 방식이 아니라:

> 의미 있는 데이터 레코드 ↔ Evidence

관계로 관리한다.

예:
- Texture Profile → Evidence
- Safety Rule → Evidence
- Storage Rule → Evidence
- Cooking Time Guidance → Evidence

### 대표 + 보조 Evidence

여러 출처가 있는 경우:

**대표 Evidence 1개 + 보조 Evidence 여러 개**

구조를 사용한다.

대표 Evidence:
- 가장 강한/권위 있는 근거
- 실제 서비스 데이터의 기준

보조 Evidence:
- 동일 내용을 뒷받침
- 추가 맥락 제공

출처가 서로 충돌하면 임의로 합치지 않는다.
충돌이 크거나 안전에 영향을 주면 `NEEDS_REVIEW`.

### Evidence에 필요한 메타데이터

가능하면:
- organization
- title
- url
- source_tier
- published_at
- retrieved_at / checked_at
- applicability
- status

를 관리한다.

`published_at`과 `retrieved_at`은 출처 발표 시점과 우리가 확인한 시점을 구분하기 위한 것.

---

## 6. 출처 우선순위

**결정: C**

모든 데이터에 동일한 출처만 강제하지 않는다.

데이터 성격에 따라 출처 우선순위를 다르게 적용한다.

### 안전/알레르기
정부/공공기관 및 공신력 있는 의료/전문기관을 최우선.

예:
- CDC
- USDA
- FDA
- NHS
- AAP
- 식품의약품안전처(MFDS)
- 질병관리청 등

### 조리/손질/TIP
공식기관 자료를 우선하되, 필요한 경우 신뢰할 수 있는 전문 조리/영유아 식품 자료도 활용할 수 있다.

핵심은:
- 안전정보는 더 엄격하게
- 일반 조리정보는 실용성과 근거를 함께 고려

---

## 7. 출처 간 충돌

**결정: C**

예:
- 출처 A: 8~10분
- 출처 B: 10~12분

이 경우 임의로 평균하거나 새로운 8~12분 값을 만들어내지 않는다.

원칙:
- 대표 출처의 값을 서비스 기준으로 사용
- 다른 출처는 보조 Evidence로 보관
- 차이가 크거나 안전에 영향을 주면 `NEEDS_REVIEW`

---

## 8. 데이터 검증 상태

사용할 상태:

- `VERIFIED`
- `INFERRED`
- `NEEDS_REVIEW`
- `UNSUPPORTED`

중요:
**재료 전체의 검증 상태와 개별 데이터의 검증 상태를 분리한다.**

예:

당근:
- 전체: VERIFIED
- Cooking: VERIFIED
- Texture: VERIFIED
- Storage: NEEDS_REVIEW
- TIP: VERIFIED
- Safety: VERIFIED

재료 전체가 VERIFIED라고 해서 모든 세부 데이터가 VERIFIED인 것은 아니다.

### UNSUPPORTED / 미등록

정보를 찾지 못했다고 재료 자체를 제외하지 않는다.

예:
- 조리시간 근거 없음 → 조리시간 미등록
- 보관기간 근거 없음 → 보관정보 미등록

---

## 9. 사용자에게 미등록 정보를 보여주는 방식

**결정: B**

정보가 없으면 조용히 숨기기보다 필요한 경우 명확하게 알려준다.

예:

> ⏱ 조리시간
> 확인된 조리시간 정보가 없습니다.
> 아래 타이머로 직접 시간을 측정할 수 있어요.

단, 다음은 구분해야 한다.

- "정보가 없다"
- "해당 정보가 필요하지 않다"

둘을 동일하게 표시하면 안 된다.

---

## 10. 출처 업데이트 및 데이터 변경

출처가 업데이트되면:

**C**
- 변경된 Evidence와 연결된 데이터만 우선 재검토
- 일정 주기로 전체 데이터도 감사/샘플링

단, 과거 데이터 버전까지 별도로 관리하지 않는다.

사용자 관점에서는 최신 데이터로 업데이트하면 된다.

**데이터 버전 이력 관리: A — 불필요**

현재 데이터가 어떤 Evidence에 의해 만들어졌는지는 유지하지만, 과거 값 자체를 계속 저장하지 않는다.

### 안전정보 변경

**B**
- 일반적인 데이터 변경 → 최신 데이터로 조용히 교체
- 중요한 안전정보 변경 → 향후 사용자에게 업데이트 사실을 알릴 수 있도록 설계

---

## 11. 상용화 기준에서 과도하게 만들지 않는 것

DB와 앱을 불필요하게 무겁게 만들지 않기 위해 다음은 현재 만들지 않는다.

- 별도 Tip 테이블
- 별도 Texture Mapping 테이블
- 별도 Cooking Method 테이블
- 별도 Ingredient Version 테이블
- 과거 데이터 전체 버전 관리 시스템
- 모든 데이터를 거대한 JSON 하나에 저장

핵심 데이터는 구조화하되, 의미 없는 테이블 분리는 피한다.

## 12. DB 구축 작업 방식

### 도구 역할

**ChatGPT**
- 조사
- 구조화
- 출처 판단
- 데이터 필드 분류
- 최종 검수

## 13. 실제 데이터 구축 순서

한 번에 30~100개를 조사하지 않는다.

### 1단계
**당근 1개를 처음부터 끝까지 완성**

검토 항목:

1. 기본정보
2. 손질/전처리
3. 조리방법
4. 조리시간
5. 익힘 확인
6. 질감 4단계
7. 안전
8. 알레르기
9. 보관
10. TIP
11. Evidence
12. 각 데이터의 verification status

### 2단계
당근 데이터를 실제 기준 데이터로 검증.

필요하면 이 과정에서 DB 스키마를 최소 수정.

### 3단계
기준이 확정되면 나머지 기존 재료를 같은 방식으로 재검증.

### 4단계
기존 재료 기준이 안정되면 신규 재료를 20개 → 30개 → 50개 식으로 확장.

## 14. 최종 의사결정 원칙

우선순위:

1. 영아 안전
2. 실제 사용자 문제 해결
3. 정확성 및 신뢰성
4. 사용 편의성
5. 유지보수성
6. 확장성
7. 개발 편의성

"AI로 만들 수 있다"는 이유만으로 정보를 추가하지 않는다.
